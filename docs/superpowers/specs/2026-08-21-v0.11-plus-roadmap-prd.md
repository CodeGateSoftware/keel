# PRD — The v0.11+ roadmap: deepen the moat, attack throughput and fees

**Status:** accepted · **Date:** 2026-08-21 · **Milestones:** 20 (v0.11), 19 (research), 15 (venues), 18 (distribution)

## The ask

> A proposal arrived to rewrite keel as a native Go application — sub-millisecond execution, a
> Bubbletea TUI, a 300-indicator TA library — while "stealing" features from Jesse, Freqtrade,
> Hummingbot and OctoBot: Optuna optimization, FreqAI adaptive ML, Telegram control, agentic
> execution, hot-swappable strategy tentacles, and prediction markets (Polymarket).

## The answer in one paragraph

No rewrite. The Python engine stays, because its auditability and its accumulated evidence base
**are** the product, and because the claimed payoff — speed — addresses the one component that is
never the bottleneck. keel's binding constraints are statistical throughput (100 pooled trades
carry ~39 effective observations; 258 pooled are needed for the n_eff = 100 everyone assumed
"n=100" meant; #427) and fee economics (the taker fee is the entire result; the fee-free
allowance is the profitability boundary). The sequence below ships what main already holds, lands
the research suite before the 2026-09-30 pooled review, then attacks venues and economics, then
polishes distribution. Everything that would erode the gauntlet, the compliance posture, or the
honest result is refused, with reasons.

## 1. Why the Go rewrite was rejected

| claim | evidence against |
|---|---|
| "sub-millisecond execution" matters | The clock is ONE_HOUR bars; ~49.4 signals per asset-year (#359). The engine is not latency-bound. |
| "near-zero startup, tiny footprint" matters | Startup cost is a packaging problem, already solved by freezing (#458, #459) and the app (#463). |
| a compiled core is better | Every published number — 0 of 90, 0 of 82, the 14.9% vs 14.88% break-even, the WAL/allowance findings — was produced by the Python engine. A rewrite restarts the evidence base at zero, and the promotion gauntlet re-derives from scratch. |
| operators want native | The browser surface (#452) is the direction every comparable project converged on (see the desktop-distribution PRD's evidence table). |

The one legitimate kernel — distribution friction — is fully in flight without touching the
engine's language (milestone 18).

## 3. A terminology correction this plan must record

**WAL is SQLite write-ahead logging** (#470: readers never block the writer; watching a fetch no
longer kills it). It is not an "allowance ledger." The two rails that are about allowances and
withdrawals are rail 14 (fee-free volume allowance — whose setting lives in the database, #310)
and rail 17 (§65.4 *qabd*, withdrawal capability). In a product whose pitch is precision about
compliance terms, invented backronyms are defects.

## 4. The sequence

### v0.11 — ship what main holds (milestone 20, #474)

25 commits past v0.10.0: the browser surface, the setup path (checklist #455, keychain #464,
credential form #465, background market data #467, browser attest/promote #469), WAL (#470), and
the macOS app (#463). The website announces it automatically (changelog page, keeltrading.com#49).

### Research suite — before the 2026-09-30 review (milestone 19, due 2026-09-29)

#443 doctor, #441 Monte Carlo, #475 rule significance, #476 Optuna, #477 read-only MCP, plus
#440/#445. All of it feeds the pooled review (#427, anchored in Phase 11, due on the review
date), which must apply the n_eff correction — 100 pooled trades carry roughly 39 independent
observations (DEFF 2.58, ICC 0.21).

**The correction stated in full (#427).** The review's n=100 floor (#353, scheduled in #359 for
2026-09-30) treats 100 pooled trades as 100 observations; they are not, because the signals fire
in herds (k = 8.43 assets/episode) and win or lose together (ICC 0.212). The executable source of
every number below is `keel/research/throughput.py`, pinned by
`tests/research/test_throughput.py`:

| quantity | value | throughput.py |
|---|---|---|
| design effect | 2.57516 | `design_effect()` |
| n_eff at n = 100 pooled | 38.8 → **39** | `n_eff(100)` |
| detectable edge at n_eff 39, 80% power, one-sided 5% | **19.9 points** (12.4 if independent) | `detectable_edge(39)` |
| edge → n_eff → pooled | 12.4 pts → 101 → **259** | `required_n_eff(0.124)` |
| | 10 pts → 155 → **399** | `required_n_eff(0.10)` |
| | 7.5 pts → 275 → **708** | `required_n_eff(0.075)` |
| | 5 pts → 619 → **1,593** | `required_n_eff(0.05)` |

pooled = ceil(required_n_eff × DEFF); displayed n_eff is ceil'd, so 101 × 2.57516 ≠ 259 exactly
is the display convention.

**Recommendation on record (decision stays with the review's owner): reframe the 2026-09-30
review as descriptive, not as a pass/fail gate.** The cross-verification's break-even arithmetic
(`docs/research/2026-08-20-quant-lab-note-cross-verification.md` §5) is what fixes the edge size
worth powering for: inside the fee-free allowance `p_be` = 14.88% against a reconstructed 14.9%
win rate — the plausible edge at the fee actually paid is within 0.6 points of zero; outside
the allowance the rules are 14 points underwater and no detectable edge rescues them. So the
only edge worth a confirmatory test is small, a 5-point edge needs n_eff ≈ 619 → **1,593 pooled
trades** — ~50 years at Basic hourly throughput after the #426 fix, ~13 years even at DCA-sized
notional ($50 per buy, `config.yaml`'s `dca.budget_usd`, gives 10 trades/month at the $500
allowance → 1,593/10 ≈ 159 months) — while the minimum honest floor (259 pooled = n_eff 101,
what "n=100" was assumed to deliver) can itself only confirm a 12.4-point edge the backtest says
does not exist. The
review should therefore report what it can measure — forward outcome rates with n_eff-corrected
intervals via `keel/research/significance.py`, rail-veto telemetry, accrual vs expectation — and
state in the report itself: *"at this n_eff the review can only see an edge of X points or
larger."* A confirmatory pooled gate, if the owner wants one, starts at 259 pooled trades (the
`min_trades` setting counts pooled trades — 259 pooled is n_eff ≈ 101; `keel/commands/rules.py`)
and reaches the edges the economics admit as plausible only at 1,593.

### Venues & economics (Phase 12 / milestone 15)

Alpaca Phase B/C (#370, #371), cash-account posture (#372), and #478: route **within** fee-free
allowances across venues. Guardrail: rail 14's cap is never relaxed to trade more — the work
moves trades into the allowance, never enlarges it. Success is stated in n_eff, with an honest
time-to-detection estimate per venue mix.

### Installer polish (milestone 18)

#479: a `curl | bash` that bootstraps the wheels — the no-warning path. #438 signing stays
budget-gated ($99/yr Apple, ~$120/yr Azure; see desktop-install.md). #439 decides the update
path the installer composes with.

## 5. Guardrails that outrank any feature

1. Rail 14 is the profitability boundary, not a budget cap to tune.
2. Typed human confirmations; the modelling proposes, keel disposes.
3. Categorical declines: futures, margin, shorting, derivatives — and prediction markets.
4. Evidence metrics in n_eff (DEFF 2.58), never raw pooled n.
5. No capability ships that the #453 declaration cannot prove is human-gated or absent.

## 6. What would change this plan

- A code-signing budget → milestone 18's shape changes (signed app distribution).
- A venue fee-structure change → #478's economics re-derive.
- Real profile trade flow arriving at scale → FreqAI-style adaptation becomes testable rather than fashionable.
- A profiled, measured compute bottleneck → a bounded Go/Rust leaf (market-data daemon) with golden-file parity against Python — extract a leaf, never replant the tree.
